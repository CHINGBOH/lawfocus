# 经济法知识图谱与合规推理系统

## 数据库、图谱与规则引擎初步设计

> 目标：建立一个支持法律历史版本、条文穿透、概念关联、上市公司治理结构建模、规则执行、合规判断和证明链回溯的经济法知识系统。

---

# 1. 系统目标

本系统不是普通法律全文检索系统，也不是单纯依赖向量检索的大模型问答系统。

系统目标是建立：

\[
\boxed{
法律原文仓库
+
时态法律知识图谱
+
结构化规则仓库
+
上市公司治理事实图
+
合规推理引擎
+
证明链系统
}
\]

整体过程：

```text
现实法律文件
    ↓
法律版本与条文结构化
    ↓
法律概念抽象
    ↓
法律规则形式化
    ↓
上市公司治理事实建模
    ↓
规则匹配与约束求解
    ↓
合规结论
    ↓
反向穿透到事实、证据、规则、法条、原始文件
```

# 3. 核心设计原则

## 3.1 原始法律不可覆盖

原始法律文件作为最高溯源依据，必须保存：

- 原始 PDF
- 原始 HTML
- 官方发布机构
- 官方链接
- 发布日期
- 生效日期
- 失效日期
- 文件哈希

原始文件只能新增版本，不应直接覆盖。

---

## 3.2 法律概念与法条分离

法律概念不能绑定固定条号。

例如：

```text
概念：股东会职权
    ├── 2018版公司法对应条文
    └── 2023修订公司法对应条文
```

因此：

\[
Concept \neq Article
\]

条文是概念在特定法律版本中的文本载体。

---

## 3.3 规则与条文分离

一条法条可以形成多个规则。

一条规则也可能由多个条文共同支持。

因此：

```text
法条
  ↓ 解释与形式化
规则
  ↓ 执行
法律结论
```

---

## 3.4 事实与证据分离

事实：

```text
甲公司董事会有9人
```

证据：

```text
甲公司2025年年度报告第67页
```

关系：

\[
Supports(Evidence, Fact)
\]

---

## 3.5 结论必须保留证明链

系统不能只保存：

```text
不合规
```

必须保存：

```text
事实
  +
规则
  +
计算过程
  +
规则优先级
  +
证据
  ↓
结论
```

# 6. 不变量设计

不变量分为三类。

---

## 6.1 本体不变量

例如：

\[
IndependentDirector\subseteq Director
\]

\[
ListedCompany\subseteq Company
\]

---

## 6.2 结构不变量

例如：

\[
Board(b)\Rightarrow \exists c:OrganOf(b,c)
\]

每个董事会必须属于某一公司。

\[
MemberOf(x,Board)\Rightarrow Person(x)\land HasRole(x,Director)
\]

---

## 6.3 规范不变量

规范不变量必须带时间。

\[
Invariant(t)
\]

例如：

\[
ListedCompany(x)\Rightarrow MustHave(x,Board)
\]

只在对应法律规则有效期间成立。

# 7. 上市公司治理符号模型

定义上市公司治理状态：

\[
G_t=(S,O,R,P,D,E,C)
\]

其中：

| 符号 | 含义 |
|---|---|
| S | 主体结构 |
| O | 组织结构 |
| R | 角色结构 |
| P | 权力结构 |
| D | 义务结构 |
| E | 行为与事件 |
| C | 合规状态 |

示例：

```text
ListedCompany(A)

AuditCommittee(C)

```

# 9. 事件节点设计

复杂关系不要直接做边，应提升为事件节点。

例如：

> 张三于2025年1月1日起担任甲公司独立董事。

建模：

```text
张三
  ↓ APPOINTEE
任职事件 E001
  ├── ROLE_TYPE → 独立董事
  ├── IN_COMPANY → 甲公司
  ├── VALID_FROM → 2025-01-01
  └── SUPPORTED_BY → 任职公告
```

事件数据结构：

```json
{
  "event_id": "E001",
  "event_type": "APPOINTMENT",
  "person": "P001",
  "company": "C001",
  "role": "INDEPENDENT_DIRECTOR",
  "valid_from": "2025-01-01",
  "valid_to": null,
  "evidence": ["EV001"]
}
```

# 10. 规则DSL初步设计

法律专家不应直接维护Python代码。

建议设计法律规则DSL。

示例：

```yaml
rule:
  code: BOARD-001
  name: 上市公司董事会设置要求

  applies_to:
    type: ListedCompany

  when:
    listed: true

  modality: OBLIGATION

  require:
    has_organ: Board

  unless: []

  consequence:
    missing:
      status: FAIL
      severity: HIGH

  source:
    articles:
      - ARTICLE-001

  valid:
    from: 2024-07-01
    to: null
```

编译后：

```python
def evaluate_board_rule(company):
    if company.listed and not company.has_organ("Board"):
        return "FAIL"
    return "PASS"
```

# 18. 最终系统定义

最终系统可以形式化为：

\[
\mathcal{L}
=
(O,R,I,F,N,T,P,E,C)
\]

其中：

| 符号 | 含义 |
|---|---|
| O | 法律对象 |
| R | 对象关系 |
| I | 不变量 |
| F | 企业事实 |
| N | 法律规范 |
| T | 时间 |
| P | 规则优先级 |
| E | 证据 |
| C | 法律结论 |

推理过程：

\[
Reality
\rightarrow
FormalFacts
\rightarrow
ApplicableRules
\rightarrow
ConstraintSolving
\rightarrow
LegalState
\rightarrow
ProofGraph
\]

数据库承担：

```text
法律虚拟机的长期记忆
```

图谱承担：

```text
法律对象之间的指针网络
```

规则引擎承担：

```text
法律规则的执行
```

证明链承担：

```text
法律结论的执行轨迹
```
