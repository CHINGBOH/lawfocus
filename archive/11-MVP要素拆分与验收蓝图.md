# MVP 要素拆分与验收蓝图

> 目的：把仓库中分散的语义、数据、规则、UI、治理和验收要求收敛为可实施的 MVP 工作基线。本文件用于排期、开发和验收；不把演示数据、自动化测试或工程状态机当作正式法律意见。

## 1. 权威顺序与范围决策

发生冲突时按以下顺序判断：

1. `法律形式化元模型与精确语义规约.md`：类型、真值、时间、冲突与证明语义。
2. `法律对象与关系词典.md`、`法律规则数据结构设计规范.md`：允许的对象、关系和规则结构。
3. `经济法知识图谱与合规推理系统-数据库与图谱设计.md`：存储、图谱与执行架构。
4. `经济法知识仓库_UI功能设计文档.md`、`MVP产品需求与验收标准.md`：用户任务、P0 范围和验收。
5. `01` 至 `05` 号专项基线：法源、十条规则、权限、性能和数据治理。

`GOAL.md`、`06` 至 `10` 号文档是工程计划或状态记录，不能降低上述约束。尤其是：**骨架完成不等于产品完成**；法律阅读主链优先于继续扩张演示规则、Docker 或性能工作。

MVP 只解决“上市公司治理合规”的一个可解释闭环：

```text
打开/检索法律 → 版本、目录和条文阅读 → 概念及来源
→ 录入或核对公司治理事实与证据 → 固定时点评估固定规则集
→ 五值结论 → 穿透规则、事实、证据和法源
```

不做全领域经济法、自动法律意见、由 LLM 补造事实/规则，或以向量相似度和模型置信度替代法律真值。

### P0 / P1 边界

| 能力 | P0 决策 | 说明 |
|---|---|---|
| 法律版本 | 版本选择、有效期、历史定位 | 原文只增新版本，不覆盖旧文本。 |
| 版本对比 | P1 | 可视化 diff 延后；P0 仍须能定位不同版本。 |
| 阅读目录 | P0 | 章节/条号树、上一条/下一条、官方来源。 |
| 检索 | P0 基础检索 | 法律名、条号、概念、公司入口；语义检索 P1。 |
| 规则 | P0 十条范围、至少逐条可治理 | 只有绑定 `VERIFIED` 直接法源且双审通过者才可进入正式规则集。 |
| 公司材料 | P0 结构化事实和证据元数据 | 批量导入、文件预览和协同流程可后续增强。 |

## 2. 不可违反的领域与信任不变量

| 要素 | 必须实现 | 禁止做法 |
|---|---|---|
| 对象 | 自然人、角色、任职、组织、事件、事实、证据、规则、结论分开建模 | 用“某人是董事”替代 `RoleAssignment`；把事实和结论混为一条记录。 |
| 法律内容 | `LegalDocument → LegalVersion → ArticleVersion` 可追溯；规则引用具体 `ArticleVersion` | 覆盖旧原文；用二手解读生成正式规则。 |
| 时间 | 有效时间使用 `[valid_from, valid_to)`；交易时间另存 | 把记录创建时间当法律生效时间。 |
| 真值 | 固定 `TRUE/FALSE/UNKNOWN/CONFLICT/NOT_APPLICABLE` | 缺记录即 `FALSE`；用“风险分”替换五值。 |
| 冲突 | 按 `(Authority, Specificity, ExceptionLevel, TemporalOrder)` 消解；不能消解则 `CONFLICT` | 按录入顺序或模型置信度挑一条。 |
| 证明 | 每个结论关联规则版本、输入事实、证据、法源和步骤 | 只返回结论文案或模型推理。 |
| 规则发布 | 草稿、法律审核、技术审核、测试、发布、废止均留版本与审计 | 已发布规则原位修改；编辑者审核自己。 |
| Agent | 只能检索辅助、组织已审核文字、产生草稿候选 | 创建已审核事实、改变真值、发布规则、决定权限。 |
| 租户与证据 | 后端强制 `tenant_id`；证据访问、导出、删除均审计 | 仅靠前端隐藏；把证据正文写入普通日志。 |

## 3. MVP 能力拆分与交付物

### E1：权威法源与版本库

**用户结果**：能确认“读的是哪一版、何时有效、来源在哪里”的公司法及直接引用规范。

- 数据：原件、SHA-256、官方 URL、公布/施行/失效/过渡时间、目录层级、审核状态；每次抓取新建 `LegalVersion`。
- 后端：按法律、版本、章节、条号和评价时点获取条文；返回来源与相邻条文。
- 前端：法律列表进入目录或第一条，绝不能固定跳转某一演示条文；阅读器左栏为真实目录，不是代码/版本/条号静态文本。
- 当前真实材料若为机器导入，保持 `UNVERIFIED`；人工核验原件、266 条切分和版本有效性后才可标为 `VERIFIED`。

**最低接口**：

```text
GET /api/v1/laws
GET /api/v1/laws/{law_code}/versions
GET /api/v1/laws/{law_code}/versions/{version_name}/articles
GET /api/v1/laws/{law_code}/versions/{version_name}/articles/{article_no}/navigation
GET /api/v1/laws/{law_code}/articles/{article_no}/effective?at=
```

**验收**：在同一浏览器会话可打开公司法第 1、108、266 条；切换版本后目录、正文、生效信息和来源同步变化；上一/下一条不丢失版本与阅读上下文。

### E2：溯源概念与“小综合”

**用户结果**：在条文中点击“独立董事”等概念，看到定义、语境、审核状态和来源；右栏只展示有依据的短综合。

- `Concept`、`ConceptVersion` 与法律条文、上下位概念及语境建立显式关系。
- API 返回 `text_segments[]`；前端仅据其中的 `concept_id` 渲染链接，不得用字符串匹配“猜”概念。
- 无已审核定义或综合输入时，明确展示“资料不足/暂无经审核综合”，不让 Agent 常识补写。
- 概念详情返回后保留法律、版本和条号上下文。

**验收**：AC-01 和 AC-08 通过：概念浮层可看到版本/有效期/来源；无审核来源时无概念链接、无新的法律命题。

### E3：公司治理、事实与证据工作区

**用户结果**：合规人员按公司、董事会、委员会、任职、控制、证据组织资料，而不是编辑 JSON 或 UUID。

- 主体：上市公司、组织机构、自然人、角色类型、任职和事件分离展示。
- 事实：结构化命题、状态和有效期间；“事实不存在”必须有支持其否定的材料，不能由空列表推断。
- 证据：标题、来源 URL/对象键、页码或定位、原句摘录、发布日期、支持关系、审核状态；事实与证据通过关联表连接。
- 页面：公司治理全景、事实卡、证据详情、创建与关联；JSON 只放高级展开区。
- 权限：组织数据只对所属租户和授权角色可见；读写、导出、删除都由后端复核并写审计。

**验收**：使用业务入口选中公司后，创建事实、创建证据元数据、建立关联、刷新后仍可查看有效期间和来源；跨租户与 Reader 读取私有材料均为 401/403 且留审计。

### E4：十条规则、规则集与确定性执行

**用户结果**：在固定评价时点，以固定、可追溯的规则集检查一家公司；每条结论都可解释。

| Rule ID | 规则主题 | 最低输入 |
|---|---|---|
| `GOV-ORG-001` | 董事会存在性 | 上市状态、组织记录 |
| `GOV-AUD-001` | 审计委员会设置 | 板块、评价时点、委员会 |
| `GOV-ID-001` | 独董最低人数 | 董事/独董有效任职 |
| `GOV-ID-002` | 独董最低比例 | 董事总数、独董人数 |
| `GOV-AUD-002` | 审计委员会成员构成 | 委员及角色 |
| `GOV-AUD-003` | 审计委员会独董占比 | 委员总数、独董委员数 |
| `GOV-AUD-004` | 召集人资格 | 召集人、独立性、专业属性 |
| `GOV-ROLE-001` | 董事任职有效性 | 任命、任期、主体 |
| `GOV-TIME-001` | 评价时点有效性 | 有效区间、评价时点 |
| `GOV-CTRL-001` | 控股/实控关系 | 持股、表决权、协议、证据 |

- 每个 `LegalRuleVersion` 至少含范围、条件 AST、要求表达式、例外、优先级、有效期、法源定位、证据策略和证明模板。
- 具体人数/比例只从 `requirement_expression` 读取；比例用整数交叉相乘，不得在处理器硬编码 `2`、`3`、`1/3` 或浮点计算。
- `RuleSet` 发布后成员与规则版本不可变；检查请求必须固定 `subject_id`、`evaluation_time`、`ruleset_id` 和 `Idempotency-Key`。
- 缺失必要事实返回 `UNKNOWN` 和 `required_fact_specs`；范围排除返回 `NOT_APPLICABLE`；例外与冲突必须列明理由及来源。

**真实法源切片规则**：已存在的单条真实绑定只能证明该规则的工程闭环，不能推及其余九条。若条文实际写“可以”或约束的是其他概念，必须拒绝错误绑定，等待正确的证监会或交易所直接法源。

**验收**：每条规则有通过、违反、边界、缺失、不适用、例外、冲突七类用例；无例外/冲突分支可书面豁免，但不得伪造执行记录。已发布的十条规则 100% 关联有效、已核验的条文版本后，才可称为正式规则集。

### E5：五值结果、预检与证明链

**用户结果**：知道结论是什么、缺什么、冲突在哪里，以及下一步去哪里处理。

| 真值 | 页面文案 | 必须展示的下一步 |
|---|---|---|
| `TRUE` | 符合 | 查看规则与依据。 |
| `FALSE` | 不符合 | 实际值、要求值、计算过程、整改入口。 |
| `UNKNOWN` | 资料不足 | 缺失事实规格和补录入口。 |
| `CONFLICT` | 事实或规则冲突 | 并列的冲突事实/规则、证据和有效期。 |
| `NOT_APPLICABLE` | 不适用 | 适用范围排除原因。 |

- 提交前预检适用规则和缺失事实；用户确认后才执行。
- `Conclusion → Proof → ProofStep` 逐步呈现：主体确认、时间、规则适用、事实读取、计算、例外、冲突、结论。
- 每一步可跳至规则版本、事实、证据和条文版本；无权限或目标被删除时显示原因。
- 结论不汇总成未定义的“合规百分制”。风险等级、置信度与真值分字段保存和展示。

**验收**：AC-02 至 AC-06 的五种状态均以真实 API 数据渲染；从一条 `FALSE` 或 `CONFLICT` 可连续打开规则、事实、证据和法源，且每个链接指向执行时固定的版本。

### E6：内容治理、权限与审计

**用户结果**：知识工程师能提交规则，审核人能双审，发布人只能发布满足门禁的版本，审计人可追踪全过程。

- 角色：`Reader`、`ComplianceUser`、`KnowledgeEditor`、`LegalReviewer`、`TechnicalReviewer`、`Publisher`、`Auditor`、`SystemAdmin`。
- 状态：`DRAFT → IN_REVIEW → LEGAL_APPROVED → TECH_APPROVED → PUBLISHED → DEPRECATED`；可转 `CHANGES_REQUESTED`。
- 发布门禁：来源有效、法律/技术双审、批准测试全绿、无未处置冲突；提交人不能终审自己。
- 审计事件至少带 `trace_id`、操作者、租户、动作、资源、资源版本、决定、原因和时间；审计追加写入。

**验收**：缺来源、测试失败、审核缺失、自审、跨租户和非 Publisher 发布均由后端拒绝；拒绝和成功路径都可在审计页筛选到。

### E7：Agent 与数据治理

- 默认 `DisabledAgentProvider`；没有密钥时阅读、规则执行和测试不受影响。
- Agent 输出是未验证候选，须经 Schema、来源、权限和人工审核后才可进入草稿；不得直接写 `Fact`、`Evidence`、规则或结论。
- `PUBLIC` 法规/公开披露材料可进入公共知识区但仍须来源、哈希和审核；`INTERNAL/CONFIDENTIAL/RESTRICTED` 按 05 号文档隔离、脱敏、最小授权和可删除。
- 本地与 CI 默认只用合成或不可逆匿名化数据。若要把公开真实材料放入本地/CI，必须先由产品、数据保护和安全责任人形成明确例外政策，禁止以“公开”自动绕过该限制。

**验收**：Agent 不可用时综合安全降级；提示注入、无来源补写和越权工具调用进入 Eval；证据导出/删除、备份和跨租户对抗测试有记录。

## 4. 最小数据与契约清单

| 域 | 不可缺少的实体/字段 | 关键约束 |
|---|---|---|
| 法源 | 文档、版本、条文版本、原件哈希、来源、效力时间、审核状态 | 版本唯一；原文追加；条文可层级定位。 |
| 概念 | 概念/版本、定义来源、关系、审核状态、文本分段 | 概念不等于条文或规则。 |
| 治理 | 主体、组织、角色类型、任职、事件 | 任职区间合法；角色与自然人分离。 |
| 事实证据 | Fact、Evidence、FactEvidence、支持关系、有效期 | 事实和证据分表；证据可多对多支持。 |
| 规则 | 规则/版本、来源、测试、审核、规则集/成员 | 已发布版本不可变；正式发布只用 `VERIFIED` 法源。 |
| 推理 | 检查、结论、证明、证明步骤、事实快照 | 记录规则集/规则版本/评价时点/幂等键。 |
| 治理 | 用户、角色、租户、审计、幂等记录 | 私有查询强制租户范围；审计追加写。 |

所有列表接口统一返回 `items/page/page_size/total` 与稳定排序。错误至少返回 `code`、`message`、`trace_id` 和可选 `details`；不得返回 SQL、堆栈、令牌或证据正文。

## 5. 推荐实施顺序：六个纵向切片

每个切片必须同步提交迁移/服务/API/OpenAPI/前端/自动化测试/运行证据；不得只堆页面或只补接口。

| 顺序 | 切片 | 交付与退出条件 |
|---:|---|---|
| V0 | 契约与基线 | 冻结本文件、OpenAPI、五值/时间/权限不变量；清理固定条号和种子 ID 依赖。 |
| V1 | 法律阅读主链（U0） | 目录、版本、1–266 条、相邻导航、来源；完成 E1 验收后再继续。 |
| V2 | 概念与小综合（U1） | 概念详情、来源、`text_segments[]`、安全空态；完成 AC-01/08。 |
| V3 | 公司资料工作区（U3） | 治理全景、事实卡、证据卡、有效期、权限与审计；完成资料录入验收。 |
| V4 | 合规与证明（U4） | 预检、十条规则集、五值结果、穿透证明、规则治理；完成 AC-02 至 AC-07。 |
| V5 | 真实法源与发布验证（U5/U6） | 法源审核、逐条真实绑定、Playwright、Docker、CI、性能、故障与恢复报告。 |

V1 至 V4 是产品可用性主链；V5 是对外发布门槛。V5 之前可演示工程能力，但不得对外表述为正式合规服务。

## 6. 验收矩阵与证据

| 编号 | 场景 | 必须可观察的结果 | 最低证据 |
|---|---|---|---|
| AC-01 | 条文与概念溯源 | 目录定位、概念定义、条文版本/有效期、返回上下文 | API/组件测试 + Playwright。 |
| AC-02 | 规则通过 | `TRUE` 与完整穿透链 | 规则单测 + E2E。 |
| AC-03 | 规则违反 | `FALSE`、实际/要求值、精确计算和来源 | 参数边界测试 + E2E。 |
| AC-04 | 资料不足 | `UNKNOWN` 与明确缺失事实 | 缺失输入测试 + E2E。 |
| AC-05 | 不适用与例外 | `NOT_APPLICABLE` 或例外条款及范围理由 | 范围/例外测试。 |
| AC-06 | 规则冲突 | `CONFLICT` 与双方规则/事实/证据 | 优先级与冲突测试 + E2E。 |
| AC-07 | 发布控制 | 后端拒绝不合格发布并落审计 | 权限/状态机集成测试 + 浏览器拒绝路径。 |
| AC-08 | LLM 边界 | 无来源不补写，禁用 Agent 可降级 | Agent Eval + UI 空态。 |
| NF-01 | 性能 | 条文读取 P95 ≤ 1s；十规则检查 P95 ≤ 3s | 固定数据集、10 分钟负载报告。 |
| NF-02 | 安全治理 | 无跨租户泄露；导出/删除可审计 | 对抗测试、审计样本、恢复演练。 |

发布前还必须具备：干净环境 Docker Compose 验证、真实 GitHub Actions 运行记录、OpenAPI 无漂移、2 小时稳定性/故障/备份恢复报告。仅有配置文件、人工走查或 `TestClient` 测试不构成浏览器或发布验收。

## 7. 当前工作项的正确判定

1. 先修复法律阅读器主链：删除法律列表固定跳转第 108 条，提供目录、版本和 1–266 条导航。
2. 再让真实公司法阅读页不混入演示概念/综合；无审核来源即显示空态。
3. 并行准备法源审核和十条规则的直接条文映射，但不以错误映射换取“完成率”。
4. 完成公司资料、预检、五值结果和证明体验后，再进入 Playwright、Docker、CI、性能与恢复。

### 统一完成定义

只有同时满足以下条件，MVP 才可标为“可交付”；否则应描述为“工程演示”或“内测”。
